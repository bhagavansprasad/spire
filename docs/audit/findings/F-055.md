## F-055 — `invoices in the last 7 days` refuses every time: the model converts days to a fractional month (`0.23`), which the planner rejects

**Date:** 2026-09-27
**Status:** confirmed
**Cross-refs:** F-054 (same `last N` family; `30 days` happens to round to `1` month and works); run `20260927_manual` N=10

### R — Reproduction

Prompt run 10 times against the current pod on 2026-09-27, captured
to `t_F055_N10.txt` (rule 15.1).

Result: 0 successes.

- 9/10 planner-guard refusal, identical message.
- 1/10 parser refusal (UNSUPPORTED_FILTER flavor).

```
=== RUN 1 ===
Router: modules=['payables']
REFUSED (planner guard): plan: created_in_last_n_months requires
value={'months': <positive int>}; got {'months': 0.23}.
```

The one non-planner-guard run:

```
=== RUN 9 ===
Router: modules=['payables']
Reason:   I can look up supplier invoices, but not the way this
          question narrows them.
```

Every failure is on the same prompt. The prompt is in scope:
`b_invoice_date.sysprompt` names `'invoices in the last 30 days'` as a
covered phrasing, and `30 days` runs correctly (F-054's N=10 shows
10/10 successes). `7 days` is the same shape with a different N.

Reproduces -> proceed to S0.

### S0 — Claim

`invoices in the last 7 days` fails every time — either the planner
rejects the parsed filter value (`{'months': 0.23}`), or the parser
refuses outright — where `invoices in the last 30 days` succeeds.

### S1 — Harm

Refusal of an in-scope prompt. The user asks a normal date-bounded
question about recent invoices. The system refuses, or errors in the
planner guard. The answer they asked for is available.

The difference is the N: `30 days` becomes `1` month; `7 days` becomes
`0.23` months.

### S3 — Mechanism

Two mechanisms fire on the same prompt, in different runs.

**Planner-guard refusal (9/10).** The model parses `last 7 days` into
the `created_in_last_n_months` filter with value `{'months': 0.23}`.
The planner's `_build_entity_fetcher_args` in
`src/spire/planner/plan_builders.py` rejects the value:

```python
if (
    not isinstance(months, int)
    or isinstance(months, bool)
    or months <= 0
):
    raise ValueError(
        f"{ftype} requires value="
        "{'months': <positive int>}; got "
        f"{raw_value!r}."
    )
```

`0.23` is not an `int`. The guard fires, `plan_node` catches the
`ValueError`, and the refusal is rendered by
`capability_message`. The sysprompt's rule for RELATIVE RECENT
(`b_invoice_date.sysprompt`) tells the model to route `last N` to a
`created_in_last_n_months` filter with value `{'months': N}` and adds
"Do NOT compute the date yourself" — but it never states that N must
be an integer, and never says how to handle a days phrasing. The model
does the natural thing: it converts 7 days to 0.23 months and passes
it through.

**Parser refusal (1/10).** On one run the model declined at parse
time with UNSUPPORTED_FILTER flavor. The exact prompt is fine per
sysprompt rules; the model judged it not to match. Same root: the
`last N days` shape is under-specified in the sysprompt, so the model
is unsteady about whether it is in scope.

### S4 — Probable root cause

A parser grammar gap: `b_invoice_date.sysprompt` treats `last N days`
as a synonym of `last N months` in the phrasing list but does not
supply the conversion. `30 days` happens to convert cleanly (1 month),
which is why the prompt in the smoke set worked and hid the shape.
`7 days` exposes it: any N where `N/30` is not an integer produces a
fractional `months` value, and the planner rejects fractional months
by design.

The sysprompt's phrasing list is doing two jobs at once — teaching
the model what shapes are in scope, and implying a conversion it does
not name. The gap is that the conversion is left to the model's own
arithmetic, which produces a float the pipeline cannot accept.

### S5 — Alternative disproven

Alternative: the model refuses because `last 7 days` is genuinely
out of scope for a `months`-typed filter, and the refusal is correct.

Disproved by the smoke set itself. `payables/smoke.txt` lists
`invoices in the last 30 days` as an in-scope prompt — the same
days-based phrasing — and it succeeds. The pipeline's own test set
declares the shape in scope. Refusing `7 days` while accepting
`30 days` is a conversion gap, not an out-of-scope judgement.

### S6 — Falsifier

Run `invoices in the last 7 days` against the current pod. If the
parser emits a valid `created_in_last_n_months` filter with an integer
months value (or a different valid filter that expresses the same
window), the claim is wrong.

### S7 — Classification

**Confirmed.** S1–S6 all pass. R reproduces every run.

### S8 — The miss record

1. Did a prompt of this shape exist? Yes — `payables/smoke` prompt 5
   is the days-based reproducer, and it passed. The failing shape is
   the same form with a different N. No smoke prompt used a
   non-integer-converting N.
2. Why did it not surface? The one days prompt in the smoke set is
   `30 days`, which converts to exactly 1 month. That N happens to be
   a whole number of months and passes cleanly. A `7 days` or
   `14 days` prompt would have caught it.
3. What would have caught it? A `date_filters` smoke prompt using a
   days count that is not a multiple of 30 — `7 days`, `14 days`,
   `21 days`. Cheap, one line.

### Fix

**Fix location:** (Phase 2's job; this records where, not what)

`src/spire/nl_parser/context/payables/b_invoice_date.sysprompt` —
the RELATIVE RECENT rule. The gap is that the rule names days and
months in the same phrasing list without stating the conversion.
Two candidate shapes:

1. **Teach the conversion.** Add a clause: for a days count,
   convert to a whole number of months and round up. This lets
   `7 days` become `1 month` at parse time and the plan runs. Cheapest
   fix; a two-line sysprompt edit.
2. **Add a `days` filter type.** Introduce `created_in_last_n_days`
   with its own tool arg (or reuse the same one with a days cutoff).
   Larger change; correct shape for the domain.

Shape 1 is the small fix. Shape 2 is the right fix if `last N days`
should be exact rather than rounded. Both require a regression test:
`invoices in the last 7 days` must produce a plan, not a refusal.
