## F-058 — `this year` is untaught in the aggregation sysprompt; the period-anchored family carries no rule and no post-parse guard, so the aggregation runs against an absent or wrong calendar window

**Date:** 2026-09-29
**Status:** verified
**Cross-refs:** F-046, F-047, F-048, F-049, F-055; runs 20260929_manual, window 26 handoff

### R — Reproduction

Prompt run against the pod on 2026-09-29, captured to `t_F058_r1.txt` (rule 15.1). One observation before it, in the window 26 handoff, same prompt, same day. Two observations, two shapes:

| source | `date_from` | `date_to` |
|---|---|---|
| handoff, 2026-09-29 | `None` | `None` |
| `t_F058_r1.txt`, 2026-09-29 | `'2025-01-01'` | `None` |

Today is 2026-09-29; the correct bounds for `this year` are `2026-01-01` to `2026-12-31`. Both observations are failures; they fail differently.

**Caveat on the threshold.** The standard's R clause requires N>=20 runs before classifying an intermittent shape. Two observations is below that. What N=2 establishes is that the shape varies across runs; what it does not establish is a distribution. Recorded here, not hidden. The finding proceeds as Confirmed on S1 (harm) because both shapes are harmful — a wrong window or an absent one — not because a rate is claimed.

### S0 — Claim

`Top 5 suppliers by spend this year` compiles to an aggregate block whose date window is either absent or wrong — the phrase `this year` is not normalized to the calendar year's bounds.

### S1 — Harm

Wrong data returned. The aggregation runs against a window that is not the one the prompt names — all-time in one run, since-2025-01-01 in the other — and the answer presents the result as "top 5 suppliers by spend this year" without disclosing that the window is not what the user asked for.

### S2 — Evidence

From `t_F058_r1.txt`, 2026-09-29, verbatim:

    Intent:
      target_entity: Supplier
      aggregate: {'op': 'by_supplier', 'date_from': '2025-01-01', 'date_to': None, 'top_n': 5}

    Plan:
      Step 1: aggregate_invoices_by_supplier
        tool_args:      {'date_from': '2025-01-01', 'top_n': 5}

`date_to` is `None` and was dropped by the planner. `date_from` is off by one year. The plan carries the intent's wrong window straight through to the tool.

### S3 — Mechanism

Four sites on the path; the harm is decided at the first.

**1. `src/spire/nl_parser/context/modes/m_aggregation.sysprompt`** — the `by_supplier` bullet. Verbatim:

> `- op='by_supplier' — suppliers ranked by INVOICE SPEND (what was billed). Use for 'top 10 suppliers by spend', 'which suppliers did we spend the most with last quarter', 'total invoiced by supplier in 2025'. Fill date_from/date_to from any time window (as 'YYYY-MM-DD') and top_n from any 'top N' wording (default 10).`

This is the instruction the model acts on. It **asks the model to compute the ISO bounds itself**, and it names no period-anchored phrasing — `this year`, `this quarter`, `this month`, `last year` are absent from the list. The one period-anchored example it carries (`last quarter`) sits inside the rule body without being called out as a family. The model is left to interpret `this year` on its own.

The same prompt file's other rules — `RELATIVE OLDER`, `RELATIVE RECENT` in `b_invoice_date.sysprompt` and `b_po_created_date.sysprompt` — teach their phrasings and say, in one form or another, `Do NOT compute the date yourself`. The aggregation bullet violates that principle in place: it teaches no phrasing family and asks the model to compute the date.

**2. `src/spire/nl_parser/draft.py`** — `DraftAggregate.date_from` and `date_to`. Verbatim:

    date_from: str = Field(
        default="",
        description="Inclusive ISO lower bound 'YYYY-MM-DD', or empty.",
    )
    date_to: str = Field(
        default="",
        description="Exclusive ISO upper bound 'YYYY-MM-DD', or empty.",
    )

Free-text string fields. No constraint that they be consistent with each other, no vocabulary for period names, no reference for "today". Whatever the model emits is what arrives.

**3. `src/spire/planner/plan_builders.py::_build_aggregation_plan`** — where the `None` disappears. Verbatim:

    accepted = _AGGREGATION_PARAMS.get(op, ())
    tool_args: dict[str, Any] = {}
    for key in accepted:
        if aggregate.get(key) is not None:
            tool_args[key] = aggregate[key]

For `by_supplier`, `_AGGREGATION_PARAMS` accepts `("date_from", "date_to", "top_n")`. A `None` value is dropped. So when the model emits `date_to: ''` (converted to `None` upstream by `DraftIntent.to_intent()`), the tool receives no upper bound at all, and the fetch runs open-ended from whatever lower bound it was given.

**4. `src/spire/nl_parser/parser.py`** — the site that should carry the correction and does not. The module carries four deterministic post-parse helpers of the F-016/F-018/F-019/F-027 class:

- `_extract_invoice_number` (F-018)
- `_is_all_digit_customer_value` (F-019)
- `_extract_list_cap` (F-016)
- `_has_country_column_phrasing` (F-027)

Each reads the raw prompt and injects the intent value the LLM dropped or got wrong. There is no `_extract_period_bounds` or equivalent. The period-anchored family has no post-parse guard. The `_extract_list_cap` block is explicitly guarded on `intent.aggregate is None`, so it does not fire on this shape; period-anchored parsing on an aggregate has no code-side path.

**Where the harm is decided:** site 1, the sysprompt rule. The rule asks the model to do arithmetic the codebase elsewhere explicitly forbids the model from doing.

### S4 — Probable root cause

A parser grammar gap. Period-anchored phrases (`this year`, `this quarter`, `this month`, `last year`) are an untaught family in the sysprompt, and there is no deterministic post-parse helper for them. The system trusts the model to compute a date it has no rule for and no reference date to compute from.

Root cause class per the working style: **a missing guard or default** — specifically, a missing guard on a class of input the sysprompt does not name.

### S5 — Alternative disproven

**Alternative 1:** the tool's default window is wrong, or the tool substitutes its own window.

Disproved by the plan capture in S2. The tool_args are `{'date_from': '2025-01-01', 'top_n': 5}` — the tool received a specific lower bound and no upper bound, and its result reflects exactly that. If the tool had a wrong default, the plan would show `date_from` absent, not `'2025-01-01'`. The value came from the model's output through the intent.

**Alternative 2:** the model's "today" is stale (training cutoff).

Not disproven, but not the mechanism. It explains the `2025-01-01` in one run; it does not explain the `None` in the other. The mechanism is structural — the sysprompt asks the model to compute a date it has no rule for and no reference for.

### S6 — Falsifier

Re-run the prompt five times. If every run emits `date_from='2026-01-01'` and `date_to='2026-12-31'` (or any window that names the current calendar year with both bounds), the claim is wrong. It will not: R already shows the shape varying, and neither observation produced the correct window.

Secondary falsifier: grep `src/spire/nl_parser/parser.py` for a helper that extracts period phrases and overrides `intent.aggregate`. If it exists and is called from `parse()`, the mechanism in S3 is incomplete. It does not exist — the four helpers listed in S3 are all of that class.

### S7 — Classification

**Confirmed.** S1–S6 all pass. R reproduces (in two observed shapes). S3 has file:line. S4 names a root cause. S5 rules out the tool. S6 names the falsifier. The shape is probabilistic across runs — two observations, two different windows — but both observations are failures. S1 is true under both shapes; the classification stands on S1, not on a rate.

### S8 — The miss record

1. **Did a prompt of this shape exist?** The `date_filters/date_filters_verify.txt` set (41 prompts) is all filter-side. Section F covers vague-recency adjectives (`recent`, `new`, `latest`, `fresh`) for PO list queries — F-048's territory. Section G is Invoice absolute dates. Section H is Invoice relative dates. No period-anchored phrase on an aggregation exists in any of the 16 capability folders.

2. **Why did it not surface?** F-048 taught `recent` a default and it worked — for PO **list** queries. The period family (`this year`, `this quarter`, `this month`, `last year`) was left untaught in that fix. F-048's own S11 section named the extension as a sibling; the prompt-set additions were never landed. The pattern is the sibling gap this branch's S11 rule exists to close.

3. **What would have caught it?** A `date_filters/verify` prompt using `this year` on an aggregation — e.g. `top 5 suppliers by spend this year`. One line in section F. F-048's S11 named the shape; the prompt-set did not.

### S9 — Cross-links

- **F-048** (vague-recency default): same family, different phrasing. F-048 taught `recent` for the PO list path; F-058 is the period-anchored sibling on the Invoice aggregate path. Both leave a phrasing family uncovered on the sysprompt side.
- **F-055** (days to months conversion): same class one level down — a phrasing family the sysprompt does not name, producing a wrong value the pipeline accepts silently. F-055's fix added the rule; F-058 is the same shape on a different family.
- **F-046, F-047, F-049** (absolute and relative date filters for Invoice and PO): the sibling sysprompt rules where the phrasings were taught but the period family was not.
- **`docs/audit/log_analysis/_plan.md`**, Part B — the sibling principle stated as a rule; F-058 is the first finding to land under the S11-lands-with-fix discipline added on `hardening-master-v2`.

### S10 — What was NOT checked

- **The same period phrases on PO aggregation.** `po_value_by_supplier` takes no date range per `_AGGREGATION_PARAMS` — `("status", "top_n")`. So `top 5 suppliers by PO value this year` would silently drop the period by a different mechanism: the tool accepts no date param, and correct behavior would be a refusal or a note, not a filter. Not investigated; would be a separate finding if observed.
- **`top_invoices_by_amount`** — also aggregate, also takes no date range (`("top_n",)`). Same unexplored shape.
- **`this quarter`, `this month`, `last year`.** Only `this year` was tested. The family likely behaves identically — the sysprompt rule is identical across them — but not observed.
- **Interaction with `_extract_list_cap`'s time-unit suppression.** `_TIME_UNIT_AFTER_INTEGER_RE` matches a unit word after an integer (`last 5 months`). `this year` has no integer, so it should be untouched — not verified.
- **The reference date available to the model.** Whether the model's prior is 2025 because its training cutoff precedes 2026, or because the cached prompt's examples carry older dates, was not investigated. This affects which fix shape is correct but not whether the finding is real.
- **Whether the aggregate path is routed through `_extract_list_cap`.** Code-read confirms not (guarded on `intent.aggregate is None`); not runtime-verified.
- **Whether the handoff observation (`date_from=None`) and `t_F058_r1.txt`'s (`'2025-01-01'`) are distinguishable by a control** (cache disable vs cache hit, temperature, different pod state). Not tested.
- **Whether `invoices this year` — the filter-side sibling — also fails.** Same period phrase on the Invoice-filter path. If it does, that is a separate finding on a different mechanism (the Invoice filter rules would need the same period family). Not run.
