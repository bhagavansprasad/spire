### S0 — Claim

The plan for `suppliers with open purchase orders` does not set
`filter_source_when_nonempty` on the PurchaseOrder traversal step, so
the parent-supplier bucket is never filtered to those with an open PO —
and nine suppliers with zero open POs appear in the answer.

### S1 — Harm

Wrong data returned. The list is the answer. Nine of the 25 rows present
suppliers with `Open POs = 0` in response to a prompt that asked for
suppliers WITH open POs.

### S3 — Mechanism

In `src/spire/planner/planner.py`, `generate_plan`'s Block 2 chooses the
step shape from two registries:

```python
filter_source_when_empty = filter_type in _FILTER_SOURCE_NAME_SUFFIX
filter_source_when_nonempty = (
    filter_type in _FILTER_SOURCE_NONEMPTY_SUFFIX
)
```

In `src/spire/planner/registries.py`, the two registries are:

```python
_FILTER_SOURCE_NAME_SUFFIX: dict[str, str] = {
    "has_no_recent_invoices": "no_recent_invoices",
}

_FILTER_SOURCE_NONEMPTY_SUFFIX: dict[str, str] = {
    "has_invoice_over_amount": "has_invoice_over_amount",
    "has_site_in_bu": "has_site_in_bu",
    "has_classification": "has_classification",
}
```

`has_open_PO` is in neither. It is edge-traversal — the KG declares it
that way, and the plan's Step 2 confirms it — but it is not in
`_FILTER_SOURCE_NONEMPTY_SUFFIX`, so the Block 2 branch falls to the
"else" shape:

```python
else:
    tool_args = {_arg_name_for_tool(tool): "$iteration_value"}
    client_filters = _resolve_client_filters(filter_spec, target_entity)
    output_name = _make_output_name(target_entity, None, [])
    new_previous_entity = target_entity
```

That branch produces `output_name: open_pos` (the child list) with no
`filter_source_when_nonempty`. The downstream synthesiser renders the
source step's suppliers joined to their children, which is why all 25
parents appear and nine show a count of zero.

### S4 — Probable root cause

A plan-template selection gap: the presence-side registry
`_FILTER_SOURCE_NONEMPTY_SUFFIX` was created for F-010's reproducer
(`has_invoice_over_amount`) and covers `has_site_in_bu` and
`has_classification`, but was never extended to `has_open_PO`. The two
filters have identical shape — iterate to a child, keep the parent if
the child call returned something — but only one was wired.

The registry is a hardcoded dict, with `registries.py`'s own header
noting "v1.2 candidate: move these into the KG itself." Until that
move, a new presence-shaped edge filter must be added here by hand.
F-010's fix added one entry; `has_open_PO` was not picked up.

### S5 — Alternative disproven

Alternative: the synthesiser is at fault — it should filter the parent
list before rendering.

Disproved by reading Step 2's plan. There is no
`filter_source_when_nonempty: True` on the failing step. The synthesiser
cannot infer the intended parent filter from the plan shape alone; the
plan is the contract. The passing sibling's plan carries the flag; the
failing plan does not. Same synthesiser, same target, different plan.
The mechanism is in the plan, not the renderer.

### S8 — The miss record

1. Did a prompt of this shape exist? Yes. `procurement_supplier/smoke`
   prompt 2 exercises it and reproduces. F-010's own reproducer was a
   different filter (`has_invoice_over_amount`), not this one.
2. Why did it not surface? F-010's fix wired exactly one filter. No
   sibling prompt was written to exercise the other edge-traversal
   presence filters (`has_open_PO`, `has_site_in_bu`,
   `has_classification`). Two of those three are wired; `has_open_PO`
   slipped through.
3. What would have caught it? A sibling-prompt check next to F-010's
   reproducer — one prompt per presence-edge-traversal filter — so
   the fix's coverage matches the mechanism's surface.
