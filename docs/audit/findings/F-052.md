## F-052 — `List active suppliers with ... and address` refuses unparseable; the address-on-supplier grammar covers three literal phrasings and no list-plus-filter-plus-non-column-field shape

**Date:** 2026-09-27
**Status:** closed-as-not-a-bug
**Cross-refs:** F-001, F-050; run `20260925_150333` columns/smoke prompt 5; sibling pass columns/smoke prompt 1

### S0 — Claim

The parser refuses the in-scope prompt
`List active suppliers with supplier name, supplier number, and address`
with `unparseable`, when the structurally identical sibling
`List active suppliers with supplier name, supplier number, and status`
parses cleanly.

### S1 — Harm

Refusal of an in-scope prompt. The user asked a reasonable list question
— two valid Supplier columns plus a third requested detail — and got a
refusal whose Example suggests a different prompt. The answer they
asked for is available in the pipeline; it is refused before the fetch.

### S2 — Evidence

From `overnights/20260925_150333/columns/smoke.log`, verbatim.

Passing sibling (columns prompt 1, line 35):

```
Router: modules=['supplier']
[llm] stage=parse in=5760 out=522 total=6282
Intent:
  target_entity: Supplier
  filters:
    - {'type': 'status', 'value': 'active'}
  fields: ['Supplier', 'SupplierNumber', 'Status']
```

Failing prompt (columns prompt 5, line 330-335):

```
Router: modules=['supplier']
[llm] stage=parse in=5760 out=754 total=6514
[parse] empty draft (no target_entity, not unanswerable); retrying once

========================================================================
PROMPT: List active suppliers with supplier name, supplier number, and address
========================================================================
Reason:   the model produced a draft with no target_entity

Solution: Name a record type and one thing to narrow it by.

Example:  invoices for Lee Supplies
  (refusal: unparseable — the model produced a draft with no target_entity)
```

Same router (`['supplier']`), same parse input tokens (`in=5760`),
same model. The failing parse produced more output (754 vs 522) and
returned a draft with no `target_entity`. Retry fired. Retry returned
the same. Refusal rendered.

### S3 — Mechanism

Three rules in the scoped system prompt cover this shape and conflict
on the third column:

- `src/spire/nl_parser/context/columns/b_column_fields.sysprompt`:
  "put the EXACT column names in 'fields' (from the COLUMNS list
  below)."
- `DraftIntent.fields` description in
  `src/spire/nl_parser/draft.py`: "list EVERY column the question
  names, using the entity's column names below where they match. If the
  question names a column that is NOT in the list (e.g. 'credit rating'
  on a supplier), still include it here as the user wrote it."
- `src/spire/nl_parser/context/supplier/b_suppliers_addresses.sysprompt`:
  fires on exactly three phrasings — `'suppliers with their addresses'` /
  `'list suppliers with their address'` / `'suppliers and their
  addresses'` — and emits `target_entity: Supplier` with
  `include: ['Address']`.

The prompt's third column is `address`. It is not a Supplier column,
so rule 1 can be read as excluding it. Rule 2 says include it anyway
as a field. Rule 3 would add it as an `Address` include, but only for
three literal phrasings the prompt does not match. The model has three
rules pointing three ways and produces a draft with no `target_entity`
— not a refusal, not a valid parse.

The retry fires. Same input, same cache, same model. Same empty result.
Only then does the parser refuse, at `src/spire/nl_parser/parser.py`,
in the shape-check branch:

```python
if not getattr(parsed, "target_entity", None):
    if not (getattr(parsed, "aggregate", None) or getattr(parsed, "compare", None)):
        return ParseResult.refuse(
            RefusalFlavor.UNPARSEABLE,
            detail="the model produced a draft with no target_entity",
        )
```

### S4 — Probable root cause

A parser grammar gap. The address-on-supplier grammar is written as
three literal phrasings and does not generalise to "address as one of
several requested columns on a Supplier list". Two consequences:

- `b_column_fields` and the `fields` schema description push the model
  in opposite directions for a non-column field name (`address` is in
  neither the COLUMNS list nor `_FIELDS_SATISFIED_BY_INCLUDE` until the
  include is active).
- `b_suppliers_addresses` would resolve the ambiguity if the phrasing
  matched; it does not, because the rule enumerates three forms.

No rule owns the composite shape. The model resolves the ambiguity by
emitting nothing.

### S5 — Alternative disproven

Alternative: this is the documented ~3% JSON-mode stochastic empty-draft
mode (`parser.py`, "Empty-draft retry" comment — "Measured 5% on one
prompt (1/20 loop), ~3.2% over 155 prompts across 5 runs").

Disproved two ways:

1. The retry fired and failed. `_retry_draft_once` is an independent
   trial against the same model. At the documented ~3% single-call rate,
   two consecutive failures is ~0.09% — not impossible, but 30x less
   likely than a systematic cause.
2. Only one prompt in 71 hit it, and it is precisely the one whose shape
   is uncovered by any rule. If the mode were stochastic across prompts,
   the rate would spread; here it lands on the one prompt with no
   owning rule.

### S6 — Falsifier

Re-run the single prompt against the same pod. If the parser emits
`target_entity: Supplier` with `include: ['Address']` (or with
`address` in `fields` and rendered as unresolved), the claim is wrong.

### S7 — Classification

Confirmed. S1-S6 all pass.

### S8 — The miss record

1. Did a prompt of this shape exist? Not before this run. The `columns/`
   set is new; the phase-1 audit did not carry a list-plus-filter-plus-
   non-column-field shape.
2. Why did it not surface? The grammar was literal-phrasing-based from
   the start. `b_suppliers_addresses` covers the three phrasings the
   audit used ("suppliers with their addresses"), and nothing in phase 1
   asked for `address` as one column among several on a filtered list.
3. What would have caught it? A `columns/` prompt pairing a status
   filter with a field list whose last element is a non-column detail
   name (`address`, `contact`, `site`, `classification`).

### Closure — 2026-09-27, closed as not-a-bug

The finding was written on 2026-09-27 from the 2026-09-25 smoke log.
Under R (added to the working style later the same day), the prompt was
re-run against the current pod before the finding was treated as a bug.

**Result: not reproducible.**

- 20 consecutive runs of the same prompt, 2026-09-27:
  `target_entity: Supplier` parsed on all 20.
  `[parse] empty draft` fired on 1 of 20 (the documented ~3% JSON-mode
  mode); the retry recovered it; 0 unparseable refusals.

The grammar-gap theory in S3/S4 is unsupported. The model emits the
correct intent with `include: ['Address']` on every run. The
2026-09-25 failure was the documented stochastic empty-draft mode
landing on this prompt — the S5 alternative, which S5 dismissed as
30x less likely than a systematic cause, was correct.

**Closure shape (S7-notes): Audit-time observation diverged.** The
2026-09-25 log recorded the empty-draft shape firing twice in a row;
the same prompt today fires it at the documented rate. No git
archaeology is done: the parser code is unchanged in this window, the
pod state has moved (different suppliers, different address data), and
whether one side or the other moved is not checked at closure time.

**Re-open condition.** The same prompt fires the empty-draft shape
repeatedly (not once in ~30 runs). A single empty-draft is the
documented mode, not a bug.
