## F-059 — `Count of suppliers` intermittently reports `There are 0 suppliers.`; the unfiltered `search_suppliers({})` fetch returns an empty list on some runs, and the tool reports the empty count as the pod's population

**Date:** 2026-09-29
**Status:** open
**Cross-refs:** window 26 handoff P3 (same step-1 shape); F-053 (sibling reproducer shares `search_suppliers({})` step 1); endpoints reference pod-reliability notes on empty collections; runs 20260929_manual r1-r4

### R — Reproduction

Prompt run against the pod five times, 2026-09-29, captured per rule 15.1 to `trash/t_F059_r1.txt` through `r4.txt`, plus one observation in the window 26 handoff. Five observations, three distinct outcomes.

| source | `Outputs:` | `Answer:` | shape |
|---|---|---|---|
| window 26 handoff | 25 records | `There are 25 suppliers.` | page size reported as the total |
| 20260929_manual r1 | 0 records | `There are 0 suppliers.` | empty fetch |
| 20260929_manual r2 | 0 records | `There are 0 suppliers.` | empty fetch |
| 20260929_manual r3 | 0 records | `There are 0 suppliers.` | empty fetch |
| 20260929_manual r4 | 25 records | `There are 6573 suppliers.` | correct |

Three of four same-day runs returned the wrong answer; the fourth returned the right one; the handoff recorded a third shape (a real fetch reported as the total rather than the pod's).

**Threshold caveat.** The standard's R clause requires N>=20 runs before classifying an intermittent shape. Five observations is below that. What N=5 establishes: the shape varies (four same-prompt runs, three outcomes), and 3 of 4 are wrong. What it does not establish: a rate. The finding proceeds as Confirmed on S1 (harm: every empty-fetch answer names a pod-wide total that is not the pod-wide total), not on a rate. The N>=20 sweep is a confirmation step.

### S0 — Claim

`Count of suppliers` intermittently returns `There are 0 suppliers.` when the pod holds thousands. On the failing runs the source fetch — `search_suppliers` with no filters — returned an empty `items` list.

### S1 — Harm

Wrong data returned. `There are 0 suppliers.` is a specific, false claim about the pod's population. A user reading it has no signal that the answer is wrong; nothing in the answer, the truncation block, or the metadata marks the fetch as failed.

### S2 — Evidence

From `trash/t_F059_r1.txt`, 2026-09-29, verbatim:

    Intent:
      target_entity: Supplier

    Plan:

      suppliers: 25 record(s)
        [1] {'SupplierId': 300000047414503, 'SupplierNumber': '1252', ...}
        ... (20 more)

The parser produces the same intent in both. The plan is identical. The tool args are identical. The pod's response is different: 0 items vs 25.

### S3 — Mechanism

Four sites on the path; the first three are stable across every observation, the fourth is where the harm lands.

**1. `src/spire/nl_parser/parser.py`** — parser produces `target_entity=Supplier, count_only=True`. Identical across all four runs. Not the site.

**2. `src/spire/planner/plan_builders.py::_build_entity_fetcher_args`** — empty filter list in, empty args dict out. `_apply_list_limit` fires only when `intent.list_limit` is set; this prompt carries no `top N`, so it is a no-op. Fetcher args stay `{}`. Identical across runs. Not the site.

**3. `src/spire/mcp_server/server.py::search_suppliers`** (the MCP wrapper) — the only thing it adds is `limit=25` (default). One async-context-manager FusionClient per call. Identical across runs. Not the site.

**4. `src/spire/mcp_server/tools/suppliers.py::search_suppliers`** — where the harm lands. The empty-args path, verbatim:

    server_clause: str | None = None
    created_from_client = created_from
    if supplier_name_contains:
        server_clause = f"Supplier LIKE '%{supplier_name_contains}%'"
    elif created_from:
        server_clause = f"CreationDate >= '{created_from}'"
        created_from_client = None

    needs_expand = country is not None or include_addresses

    needs_client_filter = (
        status is not None
        or business_relationship is not None
        or country is not None
        or created_to is not None
        or created_from_client is not None
    )

    fetch_limit = OVERFETCH_LIMIT if needs_client_filter else limit

For this prompt every filter is None. So `server_clause=None`, `needs_expand=False`, `needs_client_filter=False`, `fetch_limit=25`. The fetch params become exactly `{"limit": 25}` — one clause-less call:

    response = await client.get(SUPPLIERS_PATH, params=params)
    items = response.get("items", [])

The `matches` predicate is vacuous (every check short-circuits on a None filter), so `filtered == items` and `final_items == items[:25]`. The reporting tail, verbatim:

    if needs_client_filter and len(items) >= OVERFETCH_LIMIT:
        ...
    if not needs_client_filter and len(final_items) >= limit:
        total = await client.total_results(SUPPLIERS_PATH, server_clause)
        return ToolResult.build(items=projected, limit_applied=limit, total_available=total)
    return ToolResult.build(items=projected, limit_applied=limit, total_available=len(filtered))

Two branches are exercised across the observations:

- Fetch returns 25 items: `len(final_items) = 25 >= 25` is True; `client.total_results(SUPPLIERS_PATH, None)` returns 6573; the count is reported correctly. Matches r4.
- Fetch returns 0 items: `len(final_items) = 0 >= 25` is False; the third branch reports `total_available = len(filtered) = 0`. Matches r1-r3.

**Where the harm is decided:** in `client.get`. The tool's behavior is correct for its input — it faithfully reports an empty response as zero. `src/spire/fusion/client.py` is the next layer and was not read this window.

### S4 — Probable root cause

**Mechanism known at the tool layer, root cause unknown.** The tool sends a single clause-less fetch and reports whatever comes back. What comes back depends on `client.get`, one layer below what was read.

Three candidate root causes, none confirmable without `src/spire/fusion/client.py`:

- **Pod degraded state.** The endpoints reference documents transient pod behavior — the OWSM 401 noise note (401s with empty body for ~30 minutes mid-day, pod-side) and the empty-collection-on-a-freshly-provisioned-pod note (HTTP 200 with `count: 0`, later populates). Neither is confirmed as this shape, but both describe exactly the symptom.
- **`client.get` swallowing an error.** If the client catches HTTP errors or non-200 statuses and returns an empty dict rather than raising, the tool cannot distinguish "no rows" from "no response". The tool's shape (`response.get("items", [])`) would then collapse both.
- **No retry on transient failure.** The tool makes exactly one HTTP call. Every other tool on the same path (aggregations, lifecycle) pages with retries built into the loop; `search_suppliers` on the empty-args path does not. A single transient failure produces the empty report.

Root cause class per the working style: **a missing guard or default** — either a missing guard on the client (a failed or empty response treated as success), or a missing default behavior (no retry on the fetch).

### S5 — Alternative disproven

**Alternative:** the parser produced a different intent on the failing runs, so the tool was called differently.

Disproven by the four captures. Every `t_F059_rN.txt` shows:

- `Router: modules=['supplier']` — same
- `Intent: target_entity: Supplier / count_only: True` — same
- `Plan: Step 1: search_suppliers / tool_args: {}` — same
- No `include`, no `fields`, no filters — same

The LLM output length varies (`out=161, 339, 193, 205`) — temperature 0 still produces different token streams — but every stream parses to the identical intent. The parser is not the site.

**Alternative 2:** the synthesizer is at fault — it should source the count differently.

Disproven by the executor's own output. `Outputs: suppliers: 0 record(s)` is the executor's bucket dump, before the synthesizer sees anything. The synthesizer is honest about the executor's output. The executor is honest about the tool's output. The tool is honest about the client's output.

### S6 — Falsifier

Run the prompt 20 times back-to-back, captured per rule 15.1. If every run returns `There are 6,xxx suppliers.` with a stable four-digit count, the claim is wrong and the earlier failures were an unrelated transient. If any run returns 0, or the count varies by thousands across runs, the claim holds.

**Secondary falsifier:** inspect the MCP server log around a failing run. A 401 or 5xx status during the fetch confirms the pod-degraded candidate over client-swallow. A clean 200 with an empty `items` list confirms the pod returned nothing on its own. Either outcome narrows S4.

### Fix

**Fix location:** (this records where, not what)

- `src/spire/fusion/client.py` — the layer where the mechanism completes. Either a retry on transient failures, or a guard that distinguishes "empty response body" from "the pod returned no rows". Which, and where, cannot be decided until the file is read.
- `src/spire/mcp_server/tools/suppliers.py` — optionally, the reporting tail. The third branch (`total_available=len(filtered)`) reports the returned-row count as the total whenever the fetch is short. For this prompt the honest behavior for an empty fetch is not "0 suppliers" — it is an error, a retry, or a `total_available=None` the synthesizer narrates as "could not be determined". The current branch is correct for a genuinely short fetch (a filter that legitimately matched nothing) and wrong for an empty fetch from an unfiltered call. Distinguishing the two requires the client layer.

Neither fix is designed here; both require the client file before S3 completes to a file:line.

**Update 2026-09-29 — S3/S4 completed after reading `src/spire/fusion/client.py`.**

The client layer was read this session. S3 completes; S4's three candidates resolve to one.

**S3 completion.** `src/spire/fusion/client.py::FusionClient.get`, verbatim:

    response = await self._client.get(path, params=params)
    response.raise_for_status()
    return response.json()

Two facts that close the mechanism:

- `raise_for_status()` raises `httpx.HTTPStatusError` on any non-2xx response. It does not swallow errors. A 401, 500, 503, or connection failure propagates as an exception out of `get()`.
- `search_suppliers` in `suppliers.py` has no try/except around `client.get`. An exception from `get()` would reach `execute_plan`, which per its contract fails the whole plan — the pipeline would emit `ERROR: execute: ...`, not `suppliers: 0 record(s)`.

The observed output on the failing runs is `suppliers: 0 record(s)` in the executor's bucket dump — a successful fetch of an empty list. The only path producing that shape is a **pod response of HTTP 200 with an empty `items` array**.

**S4 resolution — root cause named.**

The three candidates named in S4 resolve as follows:

- *Pod degraded state* — **Confirmed as the mechanism.** The endpoints reference documents this exact shape for a fresh pod: HTTP 200, `count: 0`, later populates normally. The 200-with-empty-items response is a documented pod-side transient.
- *`client.get` swallowing an error* — **Disproved.** `raise_for_status()` raises; it does not swallow. A failure would have crashed the plan; the observed output shows it did not.
- *No retry on transient failure* — **Confirmed as the fix direction, not the mechanism.** The tool makes exactly one attempt and reports whatever the pod returns. A transient empty response becomes a reported zero.

Root cause, one line: **a missing retry / empty-response guard on the unfiltered `search_suppliers` fetch.** The pod documents transient empty-collection responses; the pipeline has no mechanism to distinguish "no rows" from "not yet populated" on that single fetch.

**S5 addition — a second alternative, now disproven.** The original S5 ruled out the parser. This one rules out the client:

- *`client.get` swallows an error* — disproved by the `raise_for_status()` call shown above. A failing fetch raises; the observed output shows no raise occurred.

**Fix location refined.** Two sites, and the layer question resolves:

- `src/spire/mcp_server/tools/suppliers.py::search_suppliers` — the reporting tail. When the unfiltered fetch returns an empty `items` and `needs_client_filter` is False, the third branch reports `total_available=len(filtered)=0`. Correct for a filter that matched nothing; wrong for an unfiltered call where the pod's own count is thousands.
