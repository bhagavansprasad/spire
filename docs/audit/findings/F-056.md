## F-056 — The anchor prompt returns `Synthesized response: (none)` — the F-053 four-bucket plan shape has no local synthesizer builder, so the LLM is asked to emit a 183-record response and hits the output cap

**Date:** 2026-09-28
**Status:** verified
**Cross-refs:** F-053, F-010, F-051; run `20260928_manual` (this window); handoff window 23 "What's not done"

### R — Reproduction

Run once against the current pod, 2026-09-28, captured to `t_F056_repro.txt` (rule 15.1). Prompt:

> `List US suppliers with open purchase orders, include the buyer`

The stdout file is one line:

    Synthesized response: (none)

The stderr diagnostics, verbatim from the terminal:

    [llm] stage=classify in=586 out=222 total=808
    Router: modules=['procurement', 'supplier']
    [llm] stage=parse in=8170 out=960 total=9130
    [llm] stage=synthesize in=39467 out=7985 total=47452

No `ERROR`, no `Traceback`, no `DegenerateOutputError` surface text in stdout.

Reproduces → proceed to S0.

### S0 — Claim

The anchor prompt `List US suppliers with open purchase orders, include the buyer` returns no user-facing answer at all — stdout is the fallback string `Synthesized response: (none)` — because the synthesizer's LLM call hits its output-token ceiling (`out=7985`, on a prior window and this one identically) on a four-bucket, 183-record input the F-053 plan produced, and there is no local builder for that shape.

### S1 — Harm

Silent omission. The user asks a plain, in-scope question and gets nothing. Not a refusal, not an error, not a partial answer — the marker string that means "the pipeline ran but produced no answer". The plan executed (183 records fetched, four steps run); that the fetch succeeded is invisible to the user.

### S2 — Evidence

Captured above in R. Two facts carry the finding:

- `synthesize out=7985` — and the prior window's capture of the same prompt showed `out=7985` too. Identical. This is not run-to-run variance; the model is filling its output budget to the boundary every time.
- `synthesize in=39467` — the synthesizer was handed a 39.5k-token input. That is the four output buckets (`us_suppliers` 25 records, `us_suppliers_has_open_PO` 17, `open_pos` 130, `buyers` 11) concatenated as JSON with full field sets.

### S3 — Mechanism

Three files, one chain.

**`src/spire/graph/pipeline.py::synthesize_node`** catches `DegenerateOutputError` and returns `{"synth_failed": str(exc)}` without setting `response`. The node's own docstring says the fallback exists so "the print step can show the table alone" — and then qualifies: "Only applies when the intent carries `fields`; a degenerate synthesis on a normal query still leaves `response=None` and prints no summary."

**`src/spire/rendering/formatters.py::_format_synthesized`** begins `if response is None: return "Synthesized response: (none)"`. The intent here carries no `fields` (the Intent dump shows only `filters` and `include`), so the fields-gated fallback the docstring describes does not apply. The user gets the raw marker.

**`src/spire/synthesizer/synthesizer.py::synthesize_response`** — no local builder matches the four-bucket shape. `_supplier_with_open_pos` handles exactly two buckets (a supplier bucket plus a PO bucket). `_filtered_supplier_list` handles source + matched (two buckets, no third). `po_with_children_buckets` handles PO + children. None of them accept `(us_suppliers, us_suppliers_has_open_PO, open_pos, buyers)`. The shape falls through to the LLM path. The system-prompt block for `"Supplier"` (`_SYSTEM_PROMPT_BY_ENTITY`) instructs the model to reconcile `open_pos`, `addresses`, `contact`, and `buyers` buckets all at once; the model does, until the output budget ends.

The `DegenerateOutputError` guard in `synthesize_response` fires at `out_tokens >= LLM_MAX_OUTPUT_TOKENS * 0.95 and finish_reason != "stop"`. Two identical `out=7985` runs make "the guard fired" the only plausible reading of `response is None`.

### S4 — Probable root cause

A plan-template selection gap, inherited from the shape F-053's fix created and not closed by it.

Before F-053, this prompt produced three buckets (`us_suppliers`, `open_pos`, `buyers`) and the LLM path already could not fit the response. F-053's fix file records the overrun in its V3 section: "isolated in this session (both pre-fix and post-fix reproduce ...), but not investigated." After F-053 the shape is four buckets: the parent-keeping filter now emits a `us_suppliers_has_open_PO` bucket, and the refetch step (added to let the Buyer include chain correctly) emits a second `open_pos` bucket alongside.

The synthesizer's local builders were written one shape at a time. Every two-bucket shape has a builder. No four-bucket shape does. When F-053 added the fourth bucket to make the anchor prompt's Buyer include work, it fixed the filter harm and simultaneously kept this prompt on the LLM path — with a larger payload than before. The two changes were both necessary for F-053's own reproducer and mutually reinforcing on this prompt.

### S5 — Alternative disproven

**Alternative 1:** "raise `LLM_MAX_OUTPUT_TOKENS`."

Disproved by arithmetic on the input side. The model is being asked to emit a `PurchaseOrderResponse` (or `SupplierResponse`) that transcribes 17 `SupplierRecord`s, each with `open_po_count`, a nested `buyers` list (up to 11 unique buyers aggregated across suppliers), and — following the prompt's own rule — `addresses` on each supplier too. Emitting that is easily 8k+ tokens of JSON. Raising the cap to 16k would delay the failure, not prevent it: the shape scales with the number of matching suppliers, which is bounded only by the plan. The generator of the overrun is "ask the model to transcribe every record in a 183-record payload", not "the cap is one k too low".

**Alternative 2:** "the guard is wrong; the output was not degenerate."

Disproved by the deterministic reproduction across two windows. `out=7985` twice is not variance; the model is being cut off mid-generation, not producing a valid response that the guard misclassified. And the fallback string `(none)` is only reached when `response is None`, which is only reached via the `DegenerateOutputError` catch in `synthesize_node`.

### S6 — Falsifier

Add a fifth local builder (`build_suppliers_with_open_pos_and_buyers`, or equivalent) that accepts the four buckets the F-053 plan produces — the filtered supplier list, the POs whose `SupplierId` matches them, and the buyers keyed on those POs' `BuyerId` — and returns a `SupplierResponse` directly. Re-run the anchor prompt. If the answer is non-empty and correct (17 suppliers with their buyers, no `Synthesized response: (none)`), the claim is confirmed. If the answer is still empty, the mechanism lies elsewhere.

### S7 — Classification

**Confirmed.** S1–S6 all pass. R reproduces deterministically across two windows.

### S8 — The miss record

1. **Did a prompt of this shape exist?** Yes — this is the anchor prompt, the most-cited prompt in the project. It is in `sme/sme_testcases.txt` and appears in F-053's fix file V3.
2. **Why did it not surface?** F-053's V3 isolated it ("A new finding surfaced during F-053's V3") and the window-23 handoff recorded it as a follow-up, but neither filed it. The finding was visible at the moment F-053's author added the fourth bucket; it was written down as a note in a fix file and a handoff instead of as an F-NNN. This is the same pattern F-055 records: a symptom observed at a sibling prompt, noted in passing, then surfaced later as its own finding.
3. **What would have caught it?** A V-step in F-053 that ran the anchor prompt end to end and asserted on the *answer*, not just the plan shape. F-053's V3 already ran the anchor prompt and already saw the overrun — what was missing was the finding file, not the observation.

### S9 — Cross-links

- **F-053** — the parent finding. F-053's fix created the fourth bucket; its fix file records the overrun as an out-of-scope follow-up.
- **F-010** — the sibling `suppliers with X` shape. F-010's fix (`has_invoice_over_amount`) goes through `_filtered_supplier_list` (two buckets, no refetch step) because that filter does not chain to a Buyer include. The asymmetry between F-010's shape and F-053's is why only F-053 has the four-bucket problem.
- **F-051** — the display gate. Not a cause, but relevant: `render_answer` chooses between `_format_synthesized` and `_format_projected_table` on `fields`. This intent has no `fields`, so the fallback string is what the user sees. If `synth_failed` had a display path for `fields`-less intents, the raw `(none)` might at least be a stated reason rather than a marker.
- **Handoff window 23**, "What's not done": "A new finding surfaced during F-053's V3 ... Not yet filed." — this finding closes that item.

### S10 — What was NOT checked

- **`LLM_MAX_OUTPUT_TOKENS`'s actual value.** Not in any bundle; the arithmetic in S3 assumes 8192. The finding does not depend on the exact number — the reproduction is two identical `out=7985` runs.
- **The synthesizer's exact failure mode inside the LLM call.** Whether the model hit the cap (`finish_reason != stop`) or emitted an unparseable response that `with_structured_output` returned as `parsed=None`. Both produce `response=None` and route through the same catch. Distinguishing them would matter only if raising the cap were on the table — S5 rules that out — so it does not block this finding.
- **Whether other prompts produce this shape.** Only the anchor prompt was run. Other `include=['Buyer']` prompts with a parent-keeping filter would be expected to behave the same; not measured.
- **Whether `promptkit.py` has a display path for `synth_failed`.** Not read this window; the file is not in any bundle. The visible outcome (the raw `(none)` marker) is what the user sees, whatever promptkit does internally.
- **The synthesis prompt's bucket-selection instructions for a four-bucket shape.** The `"Supplier"` system-prompt block was read; how the model actually reasoned about four buckets was not.
- **Whether a partial response (some suppliers, truncated) is achievable at a lower cap.** Not tested.

### Fix

**Fix location:** (Phase 2's job; this records where, not what)

Two candidate sites:

1. **`src/spire/synthesizer/synthesizer.py`** — add a fifth local builder, `build_suppliers_with_open_pos_and_buyers` (or an equivalent name), that accepts the four-bucket shape the F-053 plan produces and returns a `SupplierResponse` directly. Sibling of `build_suppliers_with_open_pos`, extended to attach buyers to each surviving supplier via the PO refetch bucket. No LLM call in the path, so the overrun is removed by construction. **This is the recommended shape** — the same move that closed F-010, F-020, and the PO-with-children branch: a prompt whose answer is fully determined by the executor's rows should not be paying an LLM to transcribe them.

2. **`src/spire/graph/pipeline.py::synthesize_node` / `src/spire/rendering/formatters.py`** — the display-side mitigation. When `synth_failed` is set and the intent has no `fields`, `render_answer` should not print the raw `(none)` marker; it should state the failure with the shape. Smaller fix, and a good defensive fallback for any future four-bucket shape not yet locally built.
