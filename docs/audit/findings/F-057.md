## F-057 — `spire.sh` spawns the API before MCP's port is bound; the API's one-shot lifespan connect fails and caches `pipeline_ready: false` for the life of the process

**Date:** 2026-09-28
**Status:** fixed
**Cross-refs:** PR #180; run `20260928_manual`

### R — Reproduction

`./spire.sh --stop && ./spire.sh --dev` on a fresh tree, then
`curl -s http://localhost:4002/status | python -m json.tool`,
captured 2026-09-28 (two consecutive restarts, same output):

    {
        "ok": false,
        "pipeline_ready": false,
        "error": "mcp connect failed: Client failed to connect: All connection attempts failed",
        "uptime_s": 42
    }

`./spire.sh --status` from the same session showed the API's PID
**lower** than MCP's:

    Port    Svc    State  PID
    4001    MCP    up     653286   <- highest; started LAST
    4002    API    up     653248
    4003    UI     up     653249

Post-fix, after PR #180, the same sequence produces:

    {
        "ok": true,
        "pipeline_ready": true,
        "error": null,
        "uptime_s": 3
    }

and MCP's PID is now lower than the API's (MCP 654016, API 654045).

Reproduces deterministically pre-fix, fixed post-fix → proceed.

### S0 — Claim

`spire.sh`'s full-start path spawns the API immediately after the MCP
supervisor, with no wait. Because the API's FastAPI lifespan hook
connects to MCP **once** at startup and caches any failure as a
permanent `pipeline_error`, the API is stuck reporting
`pipeline_ready: false` for the life of the process even though all
three services are actually running.

### S1 — Harm

Inconsistency between two paths, with a user-visible consequence.
`./spire.sh --dev` reports `All three up.` — the port-binding check at
the end of the script does eventually see MCP, API, and UI as `up` —
but the API is functionally degraded: `/status` returns
`pipeline_ready: false`, every `POST /prompt` returns 503, and the UI
shows the "Not connected" banner. The startup report says one thing;
the running system does another.

### S2 — Evidence

Captured in R. Three facts carry the finding:

- **PID ordering** from `./spire.sh --status`: MCP's PID (653286) is
  higher than the API's (653248). MCP was forked *after* the API, so
  the API's startup connect could not have succeeded.
- **`uptime_s: 42`** on a fresh restart with the same cached error.
  This is not a stale process; the failure fired within the first
  minute of a brand-new API process.
- **Post-fix**: `pipeline_ready: true`, `error: null`, `uptime_s: 3`,
  and MCP's PID is lower than the API's.

### S3 — Mechanism

`spire.sh`, in the full-start branch (around line 400):

    SPIRE_MCP_PORT="$MCP_PORT" \
      nohup fastmcp run src/spire/mcp_server/server.py ...
    MCP_PID=$!

    SPIRE_API_PORT="$API_PORT" \
    SPIRE_MCP_URL="http://127.0.0.1:$MCP_PORT/mcp" \
    SPIRE_UI_ORIGIN="http://localhost:$UI_PORT" \
      nohup python -m spire.api.server > "$LOG_DIR/api.log" 2>&1 &
    API_PID=$!

No wait between `MCP_PID=$!` and the API spawn. `fastmcp --reload` forks
a worker that takes a couple of seconds to bind the port; the API's
lifespan hook fires in the first few hundred milliseconds and finds
nothing listening.

The `wait_for_bind` calls at the bottom of the script run *after* all
three spawns and only **observe** the ports binding. They do not gate
the API's start. By the time `wait_for_bind 4002 API` sees the API
bound, the failure is already cached.

In `src/spire/api/server.py`, the lifespan hook is the sink:

    try:
        from fastmcp import Client
        client = Client(MCP_URL)
        await client.__aenter__()
        app.state.mcp = client
    except Exception as exc:
        prior = app.state.pipeline_error
        app.state.pipeline_error = f"{prior} | mcp connect failed: {exc}" ...

`pipeline_error` is set once and never cleared. `/status` reads it on
every request; `pipeline_ready` is derived from it and stays `false`.

### S4 — Probable root cause

A design decision that is wrong at the seam between two files. The
`spire.sh` design doc says "ports are the source of truth" — the port
is what `--status` shows, what `--stop` sweeps, and what `--dev` waits
for before reporting "All three up." But that contract only protects
*post-startup observation*. It says nothing about **inter-service start
ordering**: which dependent services require a peer to be listening
before they can successfully come up.

The API is the first such service in the project: its lifespan hook
does a hard one-shot connect at startup. That shape is not covered by
"is the port bound?" because the port isn't bound *yet* when the API
needs it. The startup path needs a barrier, not a poll.

### S5 — Alternative disproven

**Alternative 1:** "MCP itself is down or unreachable."

Disproved by two observations in the same session. First, the CLI
(`python scripts/promptkit.py --run --prompt ...`) was succeeding
throughout — it opens its own `Client(MCP_URL)` per invocation, and
those invocations reached MCP. Second, when the API was manually
restarted against the already-running MCP, its lifespan hook
succeeded on the first try (`uptime_s: 3`, `pipeline_ready: true`).
MCP was up the whole time; the API's connect window was simply too
early.

**Alternative 2:** "The 503 is a transient network issue."

Disproved by the `uptime_s` evidence: 42 seconds into a fresh process
with no successful connect in between. A transient network blip would
eventually clear on a subsequent call — the API does not retry, so it
would not clear here.

### S6 — Falsifier

Run `./spire.sh --stop && ./spire.sh --dev` from a clean state and
immediately `curl -s http://localhost:4002/status`. If `pipeline_ready`
is `true` on the first try, with no manual intervention and no delay,
the claim is wrong. It is not: the reported behaviour reproduced on
every restart before the fix.

### S7 — Classification

**Confirmed.** S1–S6 all pass. Deterministic across two consecutive
restarts pre-fix; deterministic fix post-fix.

### S8 — The miss record

1. **Did a prompt of this shape exist?** No. The test sets exercise
   the pipeline running under a *working* API; nothing exercises
   `spire.sh --dev` as a startup path. There is no test that starts
   the stack and then asserts it is actually functional.
2. **Why did it not surface?** Startup-time races are easy to miss
   because they *usually* work. On a fast machine, MCP sometimes
   binds within the API's connect window. The failure window is
   narrow enough that casual testing passes; sustained observation
   (two consecutive restarts in this session, both failing) is what
   surfaced it.
3. **What would have caught it?** A smoke test that runs
   `./spire.sh --dev` and asserts `curl /status | jq .pipeline_ready
   == true`, run as part of the same flow that exercises the UI. That
   would have failed loudly on the first run.

### S10 — What was NOT checked

- Whether the UI process has the same race. The UI reads the API's
  `/status` on page load; if the API is up but MCP is not, the UI's
  banner reads correctly (it reports what `/status` reports). What is
  not checked is whether the UI itself might have a *startup* race of
  its own against the API — the UI's startup does not appear to make
  a one-shot connect, so this is likely fine, but not verified.
- Whether `--mcp-only` mode has any ordering interaction. That mode
  runs MCP in the foreground and does not spawn API or UI, so it
  cannot race in the same way; not tested.
- Whether the runtime mode's `spire.sh` path (same script, different
  ports) has the same defect. The fix is mode-agnostic; runtime was
  not separately exercised.
- Whether other services added in future (e.g. an aggregator, a
  scheduler) will need the same barrier. The pattern is: any service
  whose startup does a hard connect to a peer needs the peer bound
  first. The fix added the MCP wait specifically; a general "wait for
  any declared dependency" mechanism is future work.

### S11 — Coverage expansion

- A shell smoke test at the repo root or in `scripts/`:
  `spire_smoke.sh` — runs `./spire.sh --stop && ./spire.sh --dev`,
  waits for the three ports to bind, curls `/status`, asserts
  `pipeline_ready: true`, exits nonzero on failure. Cheap; catches
  the class.
- A CI step (if/when CI runs integration tests) that invokes
  `spire_smoke.sh` after any change to `spire.sh`, the API's
  lifespan hook, or `SPIRE-PORTS.env`.
- A "startup ordering" section in `spire.sh`'s help text: naming
  which services depend on which, so a future addition to the script
  knows to add a wait rather than assume parallel start is safe.

### Fix

**Fix location:** `spire.sh`, in the full-start branch — insert a
bounded wait for MCP's port between the MCP spawn and the API spawn.
If MCP never binds, start the API anyway; its own timeout produces a
clearer error than a missing service would.
