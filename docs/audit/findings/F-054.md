## F-054 — `invoices in the last 30 days` compiles to a one-sided date filter; the plan admits future-dated rows by construction, but the pod currently has none

**Date:** 2026-09-27
**Status:** closed-as-not-a-bug
**Cross-refs:** run `20260925_150333` payables/smoke C-001; siblings `invoices in the last 6 months`, `purchase orders created in the last 6 months`, `purchase orders updated in the last year` (same one-sided shape); `invoices in 2024` (both bounds, unaffected); `invoices older than 6 months` (older_than, unaffected)

### R — Reproduction

Prompt run 10 times against the current pod on 2026-09-27, captured to
`t_F054_N10.txt` (rule 15.1). Four sibling `last N` prompts run once
each, captured to `t_F054_siblings.txt`.

Result: identical on every run.

```
Intent:
  target_entity: Invoice
  filters:
    - {'type': 'created_in_last_n_months', 'value': {'months': 1}}

Plan:
  Step 1: search_invoices
    tool_args:      {'invoice_date_after': '2026-08-27'}
```

- 10/10 runs emit `invoice_date_after: '2026-08-27'`.
- 0/10 runs emit `invoice_date_before`. The filter is one-sided.
- 10/10 parse `{'months': 1}` — no parse drift.
- Every date appearing anywhere in the captured file: `2026-08-27`
  (the cutoff, 10 times) and `2026-09-01` (the invoice date, 310
  times). No `2026-10-*`, `2026-11-*`, `2026-12-*`, or `2027-*`.
- 10/10 answers: `Showing 25 of 690 invoices`.

Sibling runs (one each):

- `invoices in the last 6 months` -> `invoice_date_after: '2026-03-27'`, no upper bound.
- `purchase orders created in the last 6 months` -> `created_since: '2026-03-27'`, no upper bound.
- `purchase orders updated in the last year` -> `last_updated_after: '2025-09-27'`, no upper bound.
- `invoices in the last 7 days` -> capture lost; SIB 2 diagnostic pending.

The shape generalises across every `last N` filter tested: only the
lower bound is emitted, never an upper bound.

**The prompt does not fail the same way it failed on 2026-09-25.** The
2026-09-25 smoke log recorded future-dated invoices (dated 2026-10-01
through 2027-02-01) surfacing in this window. On the current pod,
none exist.

### S0 — Claim

The plan for `invoices in the last 30 days` compiles to a one-sided
`invoice_date_after` filter with no upper bound, so future-dated
invoices — if any exist in the pod — appear in the window unqualified.

### S1 — Harm

Wrong data returned. "Last 30 days" implies a window ending today. A
one-sided filter admits future rows, and a user reading the answer
cannot tell that the window extends into the future.

### S2 — Evidence

From `overnights/20260925_150333/payables/smoke.log` (the original
observation, 2026-09-25), and `t_F054_N10.txt` (the reproduction
attempt, 2026-09-27).

Original observation, 2026-09-25:

```
Plan is search_invoices(invoice_date_after='2026-08-25') with no
upper bound. Future-dated invoices dated 2026-10-01 through
2027-02-01 appear in a "last 30 days" window without qualification.
```

Reproduction attempt, 2026-09-27, N=10: plan still one-sided; no
future-dated rows present in the pod to surface. Same shape, no harm
available.

### S3 — Mechanism

```python
# src/spire/nl_parser/context/payables/b_invoice_date.sysprompt
- RELATIVE RECENT: 'invoices in the last 6 months' / 'invoices in the
  last N months' / 'invoices from the last year' / 'invoices in the
  last 30 days' -> target_entity 'Invoice' with a
  'created_in_last_n_months' filter whose value is {"months": N}.
  Routes to the invoice_date_after tool arg; the planner computes the
  ISO cutoff from N. Do NOT compute the date yourself.
```

The sysprompt's own rule routes `last N` to `invoice_date_after` and
nothing else. The planner's `_build_entity_fetcher_args` in
`src/spire/planner/plan_builders.py` computes the cutoff from the
filter value and emits `invoice_date_after=<cutoff>`. No upper bound
is emitted, and no rule in the sysprompt instructs one.

In `src/spire/mcp_server/tools/invoices.py`:

- Line 122-123: `invoice_date_after` becomes the server clause
  `InvoiceDate >= '<cutoff>'`.
- Line 111: `invoice_date_before` is intentionally never the server
  clause (see docstring lines 21-27): a lone upper bound over-fetches
  unfiltered and can miss older records beyond the fetch window.
- Line 173: `final_items = filtered[:limit]`.
- Line 202-207: when no other client filter is active,
  `total_available = client.total_results(path, server_clause)` — the
  true server-side count of the matching set (the 690).

The tool applies no `orderBy`, so it uses the endpoint default
newest-first. The 2026-09-25 observation surfaced future-dated rows
in the top-25 with the same tool, which is evidence of that ordering.
Today none exist; the closure rests on that plus the top-25 sample.

### S4 — Probable root cause

A design decision that is wrong: the sysprompt treats "last N" as a
one-sided window (from cutoff to +inf) rather than a bounded window
(from cutoff to today). The rule is the same shape as
`older_than_n_months` (a past-only half-window) but applies it to a
case where the natural reading implies an upper bound.

The consequences are visible only when the pod carries future-dated
rows within the window, which today it does not. This is a latent
shape, not a currently-firing bug.

### S5 — Alternative disproven

Alternative: the pod on 2026-09-25 had future-dated invoices and the
pod today does not; the code is fine.

Partially true — the pod moved. But the code's shape is unchanged:
the plan still emits no upper bound. The 2026-09-25 answer was
produced by the same one-sided filter, and a future-dated row would
reappear in this plan today if one entered the pod. The alternative
explains why the harm does not fire, not why the mechanism is
correct.

### Fix

**Fix location:** no fix; latent shape only. If reopened:

The natural reading of "last N days" is a bounded window ending
today. The current pipeline emits only a lower bound, and
`invoice_date_before` on the server side is deliberately avoided —
it over-fetches unfiltered and can miss older records beyond the
fetch window (see the tool's docstring lines 21-27 and the branch at
line 111 of `src/spire/mcp_server/tools/invoices.py`).

Two shapes could close this correctly:

1. **Server-side upper bound.** Add `invoice_date_before = today` to
   the server clause alongside the existing `invoice_date_after`.
   This requires the fetch to be range-shaped (bounded on both sides),
   not just `>= cutoff`. The `has_invoice_over_amount` fix (F-010) is
   the sibling pattern: a value must travel with the child call so
   the fetch is bounded, not a lone client filter over a page.
2. **Client-side upper bound.** Filter `final_items` by
   `InvoiceDate <= today` after the fetch. Cheaper, but only
   correct within the fetched page — the count `total_available`
   would still include future rows, and the narration would
   disagree with the visible rows. Not recommended.

Either shape requires a regression test that seeds a future-dated
invoice and asserts it is excluded. Without the seed, the shape
stays latent and untestable.
