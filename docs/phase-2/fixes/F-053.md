## V0 — Fix statement

`registries._FILTER_SOURCE_NONEMPTY_SUFFIX` gains `has_open_PO`;
`plan_builders._build_iteration_args_with_computed` gains a matching
`has_open_PO` branch that sends `status='OPEN'` on the child PO call;
and Block 3 of `generate_plan` gains a re-fetch step that pulls the
surviving suppliers' PO rows back in when a downstream include needs to
chain from them — so `suppliers with open purchase orders` (with or
without an include) returns only suppliers that have at least one open
PO, and existing include-chains still resolve.

## Deviations from the F-NNN entry's suggested fix

Four.

**1. The F-053 entry names one fix site; the fix needs three.**

The entry says: add `"has_open_PO": "has_open_PO"` to
`_FILTER_SOURCE_NONEMPTY_SUFFIX` in `registries.py`. That alone routes
Block 2 into the `filter_source_when_nonempty` branch, which calls
`_build_iteration_args_with_computed` — and that function had no
`has_open_PO` branch, so it raised `NotImplementedError`. Fix #1: add
the branch (`plan_builders.py`), sending `status='OPEN'` on the child
call. Same shape as `has_invoice_over_amount` (the F-010 sibling),
which routes a value filter to the child call.

With both changes, `suppliers with open purchase orders` returns 17 of
25. But the anchor prompt — `US suppliers with open purchase orders,
include the buyer` — went from 3-step-working to
`RefusalError: Buyer is not a valid include on Supplier`: the parent-
keeping filter does not advance `previous_entity` to `PurchaseOrder`,
so Block 3's Buyer include cannot chain. Fix #2: Block 3 of
`generate_plan` (`planner.py`) gains a re-fetch step, inserted only
when the direct chain fails and a parent-keeping filter's target entity
can supply the include. Otherwise the registry addition would break an
in-scope prompt the golden does not cover.

That Block 3 gap pre-existed this branch — F-010's fix has the same
latent shape — but no test combined `has_invoice_over_amount` with a
child-entity include. F-053 surfaced it. Recorded as a scope expansion
permitted by §10 (explicit, not silent).

**2. The per-fix workflow ran out of order.** This session branched and
wrote the source fix before opening this fix file and writing V0.
FIX_PLAN §8 step 1 requires the fix file first, and §12's session-start
checklist names the same. V7 recovers the test-fails-without-fix
evidence, and this file now records the walk; the ordering discipline
was not followed. Recorded here rather than papered over.

**3. A golden prompt changed.** `suppliers_with_open_pos.txt` is the
F-053 reproducer; the fix intentionally changes its output. V5
documents every diff hunk and the one behaviour change (loss of the
per-supplier PO count and buyer columns, caused by the parent-filter
mechanism). Golden updated.

**4. Behaviour change in the answer shape.** As recorded in V5, the
filtered answer is a plain supplier list without per-supplier PO
counts. F-010's sibling behaves the same way. If counts are wanted
later, that is an executor change to carry the child count alongside
the filtered parent — a separate finding.
