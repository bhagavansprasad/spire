# Spire prompt set — 08 PO LIFECYCLE. Read by scripts/run_prompt_set.py.
# One prompt per line. Blank lines and lines starting with # are ignored.
#
# PURPOSE: the Module 5 regression set. Exercises the ONE lifecycle tool
# that backs five catalog prompts (4.A: A.2, A.3, A.4, A.7, A.10) through
# three output shapes — status matrix, executive summary, diagnostic.
#
# THE FIVE MUST ANSWER. A refusal here is a FAILURE, not a feature
# request: these are the module's delivery commitment. Everything after
# section 5 is stability probing, where a clean refusal IS correct.
#
# WHAT TO CHECK PER PROMPT — read the ANSWER, not the summary line:
#
#   1. ROUTING. Intent shows target_entity PurchaseOrder and a single
#      lifecycle_status filter whose value is the PO NUMBER as a string.
#      Any other filter, or a refusal, is a routing failure.
#
#   2. THE PAID LEG ON 701337. It must read "cannot be determined" and
#      the Paid row must show an em dash, NEVER 0.00 and never blank.
#      This is the defect the whole module was built to remove: the tool
#      used to report remaining_to_pay 398.00, asserting a debt on a PO
#      whose invoice cannot be found. A 0.00 here is a REGRESSION.
#
#   3. COPIED, NOT DERIVED. risk, risk_reasons, recommended_action,
#      lifecycle_stage and responsible_team are computed in the tool.
#      They must appear verbatim. If the wording drifts between two runs
#      of the same prompt, something is re-deriving them.
#
#   4. DERIVED SAYS DERIVED. The received amount is prorated from
#      quantity (ReceivedAmount is empty on this pod). The answer must
#      say so. A received figure presented as fetched is the
#      confident-wrong-answer failure mode.
#
#   5. UNCONFIRMED STAYS UNCONFIRMED. 701337's PayOnReceipt note is a
#      hypothesis. If any run states self-billing as the cause, that is
#      a failure.
#
# THE TWO ANCHORS
#   701337  JGA, Open.   1235.00 ordered, 398.00 received (2 of 5 units,
#           derived), 398.00 invoiced, paid UNKNOWN. Line 1 Open with
#           837.00 outstanding; line 2 Closed. Terms overridden.
#   162034  Lee Supplies, Closed. 758.00 ordered, fully received and
#           invoiced, 830.01 paid. Complete. Carries an unexplained
#           72.01 over-invoice — the PO header has zero tax, so tax does
#           NOT explain it and no answer may claim it does.


# ── 1. A.4 — status matrix. The delivery prompt. ────────────────────
# Expect: three verdicts up front; Paid "cannot be determined" on 701337
# and "yes" on 162034.
Has PO 701337 been fully received, fully invoiced, and fully paid?
Has PO 162034 been fully received, fully invoiced, and fully paid?
Show ordered, received, invoiced and paid amounts for PO 701337 with supplier details.
Is PO 162034 complete?


# ── 2. A.7 — diagnostic. Why is it stuck, and whose problem is it? ──
# Expect: stage and owner lead; the outstanding-lines table names line 1
# and 837.00. On 162034 the honest answer is "it is not open".
Why is PO 701337 still open?
What is blocking PO 701337, and which team owns the next action?
Why has PO 701337 not been paid?
Is anything blocking PO 162034?


# ── 3. A.2 — end-to-end summary, supplier setup through payment ─────
# Expect: supplier and site setup present; stage and responsible team;
# the terms override surfaced.
Give me an end-to-end summary of PO 701337 from supplier setup through payment.
Trace PO 162034 from supplier setup through to payment and tell me the current stage.
Summarise PO 701337 and identify the current lifecycle stage and responsible team.


# ── 4. A.10 — executive summary with risk and recommended action ────
# Expect: risk copied verbatim with its reasons; ONE recommended action.
# 162034 must be Medium, not Low — the 72.01 is unexplained.
Give me an executive summary of PO 701337 including risk and recommended action.
Executive summary for PO 162034 — value, delivery, invoice and payment status, risk, and what to do next.
What is the risk rating on PO 701337 and why?


# ── 5. A.3 — per-module status breakdown ────────────────────────────
# Expect: supplier status, site status, matching level, invoice approval
# and validation, payment status. NOTE the pod has no per-invoice match
# RESULT — only the configured rule (3 Way against Receipt). An answer
# claiming "1 of 3 invoices failed match" is invented.
What is the supplier status, approval status, receipt status, invoice matching status and payment status of PO 701337?
For PO 162034, show the supplier status, invoice approval status and payment status, plus any unresolved exceptions.


# ── 6. STABILITY — the same question, worded differently ────────────
# Every one of these must route to lifecycle_status. Any refusal is a
# parser gap, not a user error. Run this block TWICE and diff: the
# computed fields must be byte-identical across runs.
Has purchase order 701337 been received and paid?
PO 701337 — received, invoiced, paid?
Tell me the lifecycle status of purchase order 701337.
What stage is PO 162034 at?
Who is responsible for the next action on PO 701337?
What is outstanding on PO 701337?


# ── 7. NEGATIVE AND EDGE CASES ──────────────────────────────────────
# A clean refusal or a clean "not found" is CORRECT here. A crash, or a
# confident answer about a PO that does not exist, is a failure.
Has PO 999999999 been fully received, fully invoiced, and fully paid?
Has PO DOES-NOT-EXIST been paid?
# No PO named — the filter resolves exactly one order, so this must
# refuse rather than scan the pod.
Have all purchase orders been fully received and paid?
# Two POs named — also out of scope for a single-PO filter.
Compare the lifecycle of PO 701337 and PO 162034.


# ── 8. MUST NOT REGRESS — neighbouring routes ───────────────────────
# These share vocabulary with the lifecycle prompts but belong to other
# filters. If any of them now routes to lifecycle_status, the parser
# section is over-matching and has stolen traffic from a working path.
Show PO 162034 and its lines.
Show the invoices raised against PO 162034.
Open POs for supplier JGA.
Which suppliers have open purchase orders?
Purchase orders created before 2015.
